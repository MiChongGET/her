## 可合理由工程决定：不形成新的产品访谈

具体接口签名、表与附属记录、状态枚举、任务幂等键、来源水位、保存通知和前台调度接点、连续段标识、配置快照/服务身份指纹、许可版本，以及有界召回算法，均可在已有约束下由工程提出并说明依据。用户已确定这些选择必须保住的外部行为；无需让用户替工程选择 SQLite 列、SDK 函数或检索技术。

既有 v1 数据兼容不能假定空库，但实际结构核对及缺少许可证明时的拒绝模型使用已在 §11.1 明确。后续只读核对和最小兼容方案是工程任务，不是需要现在访问用户库才能回答的产品问题。

## 工程计划必须补成可执行契约的接缝

以下按依赖重要性排序。它们不要求更改已批准产品规则，也不阻止先编写工程计划；必须在相应实现与验收之前补足，不可用本次审阅替代证据。

1. **公开 API 全树重建的通过/阻塞判据。** 将 §11.2 的四项条件落实为隔离合成数据矩阵和逐类型保留/清理清单，再确定替代会话切换、原展示时间与 ID 映射的实现。公开声明能证明对象和限制存在，不能证明能同时保留这些不变量；尤其空会话、非活动分支、compaction 的 systemMessage、context edit 与自定义正文均须进入判据。该结果会决定后续清理任务能否展开；无法满足时按既有决定停止完整交付，不让用户以降低遗忘承诺来替代工程证明。

2. **实际发送与来源暴露记录的统一契约。** 把 §9.2 四类用途和 §10.2 每次发送记录落成同一组可核对的输入、决策、原因与失效边界，说明普通请求/工具续轮、压缩、恢复及 system prompt 分别在哪里执行，何时持久记录、何时阻止迟到输出。当前 guard 只处理文件键，异常兜底还保留 user，不能只扩一个布尔回调就视为接通。计划需保留用户自身新输入身份，同时拒绝无法确认边界的旧历史；这会决定宿主、Pi 扩展与业务服务的任务边界，无须用户再次决定许可范围。

3. **稳定来源登记与恢复的跨存储故障矩阵。** §8 已指出 Pi JSONL 与 SQLite 不是原子事务，§10.1 已要求完整单元和幂等。任务单应明确保存后、登记前、候选后、提交前后的崩溃如何识别同一来源/工作，怎样重验绑定配置与许可，怎样区分中断、失败、主动关闭取消及已完成无候选。配置版本还须覆盖一次整理实际所用参数，不能直接假定当前 profile revision 足够。该契约决定最小持久字段和恢复顺序；外部行为已由 A2/A4/A5 决定。

本报告证明的是固定设计输入之间的规划一致性和只读源码接点核对。它不证明 MemoryService 已生产装配、模型正确执行候选抽取、真实请求完成过滤、正常中断已恢复、Electron 已有面板或完整遗忘能够通过公开 SDK 完成。后续工程计划仍须绑定产品 26 个场景和 A1–A5 的适配场景，按证据种类分别验收。
