# Design

## Context

当前回收站实现位于 `src/renderer/src/TrashPanel.tsx`，使用 React hooks 管理状态。后端存储层 `src/core/storage/store.ts` 提供了单个对话的删除和恢复方法（`purgeConversation`、`restoreConversation`），通过 IPC 通道与前端通信。

现有架构：
- 前端通过 `window.her.purgeConversation(id)` 调用单个删除
- 后端使用 SQLite 事务确保数据一致性
- 删除操作会同时删除对话记录和相关消息记录

约束：
- 必须保持现有的单个操作 API 不变
- 删除操作必须在事务中执行，确保原子性
- UI 操作期间需要禁用其他交互，防止并发问题

参见 proposal.md - Why 了解功能动机。

## Goals / Non-Goals

**Goals:**
- 在前端增加批量选择和批量操作 UI
- 后端提供批量删除 API，复用现有单个删除的事务逻辑
- 保持与现有代码风格和架构一致

**Non-Goals:**
- 不修改单个恢复/删除的现有实现
- 不改变数据库 schema
- 不增加撤销功能（批量删除后无法撤销）
- 不实现批量恢复功能（仅删除操作需要批量支持）

## Decisions

### 决策 1：批量删除实现方式

**选择**：后端新增 `purgeConversations(ids: string[]): void` 方法，在单个事务中循环调用删除逻辑。

**理由**：
- 复用现有的删除逻辑和验证（检查是否在回收站中）
- 保持事务原子性，要么全部成功要么全部失败
- 实现简单，代码复用性高

**替代方案考虑**：
- 方案 A：前端循环调用单个删除 API → 拒绝，因为无法保证原子性，部分失败时用户体验差
- 方案 B：使用 SQL IN 子句一次性删除 → 可行但需要重复验证逻辑，且失败时难以定位具体对话

### 决策 2：前端状态管理

**选择**：使用 React 本地 state 管理选中状态，不引入额外状态管理库。

**理由**：
- 选中状态是纯 UI 状态，不需要持久化
- 现有代码使用 `useState`，保持一致性
- 避免增加依赖

**实现细节**：
- 使用 `Set<string>` 存储选中的对话 ID，便于快速查找和操作
- 批量操作完成后清空选中状态

### 决策 3：清空回收站实现

**选择**：清空回收站调用批量删除 API，传入所有对话 ID。

**理由**：
- 复用批量删除逻辑，避免代码重复
- 前端和后端都不需要专门的"清空"API
- 语义清晰，易于维护

**替代方案考虑**：
- 方案 A：后端新增 `purgeAllTrashedConversations()` 方法 → 拒绝，因为功能重复且增加 API 表面积

### 决策 4：UI 布局

**选择**：在回收站列表每行左侧增加复选框，头部增加全选复选框，底部增加"批量删除"和"清空回收站"按钮。

**理由**：
- 符合常见批量操作 UI 模式，用户熟悉
- 不影响现有的单个操作按钮布局
- 复选框与确认对话框的二次确认提供足够的误操作保护

**布局细节**：
- 复选框仅在列表非空时显示
- 批量操作按钮根据选中状态和操作进行状态更新（禁用/启用）
- 操作进行中时禁用所有交互元素

### 决策 5：错误处理

**选择**：批量操作失败时，显示错误信息并刷新列表，已成功删除的对话从列表中移除。

**理由**：
- 后端事务保证原子性，要么全部成功要么全部失败
- 失败后刷新列表确保 UI 与数据库状态同步
- 错误信息使用与现有单个操作一致的格式

## Risks / Trade-offs

**风险 1：大量对话批量删除时的性能**
- **风险**：如果用户选中几百个对话批量删除，事务执行时间可能较长
- **缓解**：SQLite 在本地文件上执行，通常性能足够；若未来出现问题，可考虑分批删除并显示进度
- **权衡**：优先保证原子性而非极端情况下的性能

**风险 2：操作进行中用户关闭窗口**
- **风险**：批量删除进行中用户关闭回收站面板，可能导致 UI 状态不一致
- **缓解**：操作进行中禁用关闭按钮；依赖 `mounted` ref 防止组件卸载后状态更新
- **权衡**：不阻止用户关闭整个应用，依赖后端事务完整性

**风险 3：选中状态与列表不同步**
- **风险**：单个恢复/删除操作完成后，已选中的对话可能已不在列表中
- **缓解**：单个操作完成后更新列表时，不自动清除选中状态，让用户看到哪些对话已被处理
- **权衡**：简单的实现可能让用户困惑，但保持选中状态有助于用户理解操作结果

## Migration Plan

无需迁移，纯新增功能。部署步骤：
1. 部署后端代码（新增批量删除 API）
2. 部署前端代码（新增批量操作 UI）
3. 重启应用

回滚策略：如果出现问题，回滚到上一版本，批量操作 UI 将不可见，不影响现有单个操作功能。
