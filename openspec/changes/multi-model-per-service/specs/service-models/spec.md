# Spec Delta

## Purpose

定义一个模型服务下多个模型 ID 的配置、默认模型、聊天窗口中的模型切换、按模型记录的连接测试，以及 Anthropic 模型的 1M 输出上限开关。

## ADDED Requirements

### Requirement: 一个服务可以配置多个模型并指定默认模型
系统 SHALL 允许同一个模型服务保存一个或多个模型 ID，并且 MUST 恰有一个是该服务的默认模型。服务的地址、协议和密钥由其下所有模型共用。

#### Scenario: 添加第二个模型
- **WHEN** 用户在已有一个模型的服务中添加第二个模型 ID 并保存
- **THEN** 该服务保存两个模型，原模型仍是默认模型

#### Scenario: 更换默认模型
- **WHEN** 用户把服务的默认模型改为列表中的另一个模型并保存
- **THEN** 此后在该服务下新建的对话默认使用新的默认模型

### Requirement: 保存时校验模型列表
系统 SHALL 在保存服务时校验模型列表：至少一个模型；每个模型 ID 去除首尾空白后非空且不超过 2048 个字符；ID 不重复；最多 20 个；默认模型必须在列表中。不合法时系统 MUST 拒绝保存、给出中文错误提示，并保持原有配置不变。

#### Scenario: 拒绝不合法的列表
- **WHEN** 用户保存的模型列表为空、含空白 ID、含重复 ID、超过 20 个，或默认模型不在列表中
- **THEN** 保存失败并显示错误提示，已保存的服务配置没有变化

### Requirement: 聊天窗口可以切换当前服务的模型
聊天窗口 SHALL 在服务选择器旁提供模型选择器，列出当前服务的全部模型，用户可随时切换。切换后发送的下一条消息 MUST 使用所选模型，已有消息及其模型标注不变。

#### Scenario: 切换模型后发送
- **WHEN** 用户把模型从服务的默认模型切换为另一个模型，然后发送消息
- **THEN** 发往上游的请求使用所选模型，新的助手消息标注该模型

#### Scenario: 历史消息不变
- **WHEN** 用户切换模型
- **THEN** 此前各条助手消息上显示的模型名称保持不变

### Requirement: 新对话和切换服务时使用默认模型
所选模型 SHALL 只是当前界面的选择，不写入本地数据。新建对话、切换到另一个服务、重新打开应用时，系统 MUST 选中对应服务的默认模型。

#### Scenario: 新建对话
- **WHEN** 用户把模型切换为非默认模型后新建对话
- **THEN** 新对话的模型选择器显示服务的默认模型

#### Scenario: 切换服务
- **WHEN** 用户在聊天窗口切换到另一个服务
- **THEN** 模型选择器列出新服务的模型并选中其默认模型

#### Scenario: 所选模型被删除
- **WHEN** 当前所选模型已从服务中删除
- **THEN** 模型选择器回到该服务的默认模型，不会向上游发送已删除的模型 ID

### Requirement: 发送请求时校验所选模型
系统 SHALL 在发送消息时确认所选模型属于所选服务。不属于时 MUST 拒绝发送并给出中文错误提示，不创建消息；未指定模型时 MUST 使用该服务的默认模型。重试上一次未完成的回答时，使用当前所选的模型。

#### Scenario: 未指定模型
- **WHEN** 发送请求没有指定模型
- **THEN** 系统使用所选服务的默认模型

#### Scenario: 模型不属于该服务
- **WHEN** 发送请求指定的模型不在所选服务的模型列表中
- **THEN** 发送被拒绝并提示模型不存在，对话中没有新增消息

### Requirement: 连接测试按模型分别记录
系统 SHALL 为服务下的每个模型分别保存文字和工具两项连接测试结果。测试某个模型时 MUST 使用该模型的 ID 发起请求，结果只记在该模型上；未指定模型时测试默认模型。设置面板 MUST 按模型显示这些结果，并允许选择要测试的模型。

#### Scenario: 测试非默认模型
- **WHEN** 用户选择服务中的第二个模型并运行文字测试
- **THEN** 测试请求使用第二个模型的 ID，只有第二个模型的文字测试状态改变

### Requirement: 修改服务或模型时按范围使测试结果失效
系统 SHALL 在服务的协议、地址或凭据改变时，把该服务下所有模型的测试结果重置为"未验证"。仅增删模型时 MUST 只影响被增删的模型：新增模型从"未验证"开始，其余模型的测试结果保留；仅修改默认模型、1M 开关或服务级最大输出 token 数时 MUST 保留所有测试结果。

#### Scenario: 修改地址
- **WHEN** 用户修改服务地址并保存
- **THEN** 该服务下所有模型的测试状态都变为"未验证"

#### Scenario: 新增模型
- **WHEN** 用户在已通过测试的服务中新增一个模型并保存
- **THEN** 新模型为"未验证"，原有模型的测试状态保持不变

### Requirement: 每个模型可单独开启 1M 输出上限
系统 SHALL 允许任一协议的服务下的每个模型各有一个"1M"开关。开启时，发往该模型的请求 MUST 带 1000000 的输出上限：Anthropic 和 OpenAI 兼容为 `max_tokens`，OpenAI Responses 为 `max_output_tokens`。Anthropic 下它优先于服务级最大输出 token 数。

#### Scenario: Anthropic 开启 1M
- **WHEN** 用户为 Anthropic 服务的某个模型开启 1M，服务级最大输出 token 数为 8192，并向该模型发送消息
- **THEN** 发往上游的请求 `max_tokens` 为 1000000

#### Scenario: OpenAI 兼容开启 1M
- **WHEN** 用户为 OpenAI 兼容服务的某个模型开启 1M 并向它发送消息
- **THEN** 发往上游的请求 `max_tokens` 为 1000000

#### Scenario: Responses 开启 1M
- **WHEN** 用户为 OpenAI Responses 服务的某个模型开启 1M 并向它发送消息
- **THEN** 发往上游的请求 `max_output_tokens` 为 1000000，且不含 `max_tokens`

#### Scenario: 同一服务下其他模型不受影响
- **WHEN** 同一 Anthropic 服务下另一个模型没有开启 1M，并向它发送消息
- **THEN** 请求输出上限为服务级覆盖值 8192

### Requirement: 未开启 1M 时 OpenAI 系协议的请求不变
系统 SHALL 在 OpenAI 兼容和 OpenAI Responses 服务的模型未开启 1M 时，发出与本变更之前完全一致的请求，MUST NOT 带任何输出上限字段。服务级"最大输出 token 数"仍只对 Anthropic 服务保存和显示。

#### Scenario: 未开启 1M
- **WHEN** 用户向未开启 1M 的 OpenAI 兼容或 OpenAI Responses 模型发送消息
- **THEN** 请求体中不含 `max_tokens` 和 `max_output_tokens`

#### Scenario: 切换协议后保留开关
- **WHEN** 用户把一个已开启 1M 且设置了服务级最大输出 token 数的 Anthropic 服务改为 OpenAI 兼容协议并保存
- **THEN** 该模型仍开启 1M，服务级最大输出 token 数不再保存

### Requirement: 旧数据升级后保持可用
系统 SHALL 在启动时自动升级由本变更之前的版本创建的本地数据：每个已有服务保留原有的单个模型作为唯一模型和默认模型，原有的连接测试结果归入该模型，服务、历史对话和设置全部保留。

#### Scenario: 升级单模型服务
- **WHEN** 应用打开一份旧版本数据，其中服务的模型为 `m1` 且文字测试已通过
- **THEN** 该服务有且仅有模型 `m1`，它是默认模型，文字测试状态仍为"已验证"
